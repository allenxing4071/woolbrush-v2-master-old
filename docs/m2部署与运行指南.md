## 2. 阻塞项：m2 的出网

诊断结果：m2 访问 `gamma-api.polymarket.com` 与 `google.com` 全部超时（返回码 000），
`baidu.com` 正常 200。系统代理开关 `HTTPEnable=1` 指向 `127.0.0.1:29758`，但 m2 上
**没有任何代理客户端在运行**，也没装常见的客户端 app。

好消息是 **GitHub 可达**（200，0.8 秒，`git ls-remote` 能拿到最新 commit），所以
第 1 节的 `git clone` 和后续拉代码都不受影响，缺的只是 Polymarket 这一个出口。

对比：m5 之所以能跑通，是因为它本机有 `Upnet` 进程监听 `127.0.0.1:29758`，并且
`http_proxy`/`https_proxy` 环境变量都指向它。该进程只绑定回环地址，未对局域网开放，
所以 m2 无法直接借用（已实测，12 秒超时）。

需要出网的有两条独立路径，配置方式不同：

**A. Python 采集/回测脚本** — 走环境变量，代理可用后：

```bash
export https_proxy=http://127.0.0.1:29758
export http_proxy=http://127.0.0.1:29758
python3 backtest/collect_depth.py --once --cities nyc,london
```

**B. 交易程序（Tauri app）** — 走应用内设置里的 `proxy_url` 字段，不读环境变量。
在设置弹窗里填写代理地址即可。

> 本地模型不受影响：Ollama 走 `localhost`，v2.3.0 已确保回环与内网地址一律直连、
> 不经过代理（见第 3 节）。

## 3. 本地模型（Ollama）

### 启动服务

```bash
brew services start ollama     # 注册为服务，开机自启（推荐，m2 是常开机器）
# 或临时前台运行：ollama serve
```

### 拉模型

```bash
ollama pull <模型名>
ollama list                    # 确认名称，填进 app 设置时要完全一致
```

m2 是 64GB 统一内存，31B 级别的模型很宽裕。选型的真实权衡不是内存而是**延迟**：
每轮扫描要分析 51 个城市，模型越大单轮耗时越长，而 `toolbar.json` 里
`scanInterval=0.5`（小时）给的预算是有限的。模型越大质量越好但可能跑不完一轮，
建议先用中等规模跑通，再按实际单城市耗时决定是否上更大的。

### 在 app 里配置

设置弹窗 → LLM 服务商选 `ollama`，然后：

- **URL 和 API Key 都留空** → 自动使用 `http://localhost:11434/v1/chat/completions`
- 或显式填该地址；填了 Key 则视为 Ollama Cloud，会走代理并校验 Key
- 模型名填 `ollama list` 里的名字

v2.3.0 为本地自建做的两处修改（`src-tauri/src/commands/analyze_cmd.rs`）：
原先 `ollama` 分支强制要求 API Key，且请求一律送进代理客户端，本机 `localhost`
这两条都过不去。现在 Key 变为可选（仅非本机地址才校验），并新增 `is_local_url()`
判定，回环与内网地址（`localhost`、`127.x`、`::1`、`*.local`、`10.x`、`192.168.x`、
`172.16-31.x`）一律直连。Ollama 的 OpenAI 兼容端点与云端同格式，请求体无需改动。

## 4. 运行交易程序

双击 `~/Applications/WoolBrush V2.app`。首次从别的机器拷过来若打不开，先去隔离：

```bash
xattr -dr com.apple.quarantine ~/Applications/"WoolBrush V2.app"
```

### 数据目录位置（v2.3.0 有重要修正）

数据目录是 **`.app` 同级的 `data/`**，即 `~/Applications/data/`，会自动创建。

原实现取「exe 同级目录」，而 macOS 的 `.app` 是目录包，可执行文件在
`Contents/MacOS/` 内，数据会被写进包内部——替换新版本时整包覆盖，数据库（含私钥）、
`toolbar.json` 和复盘日志会一起丢失，同时破坏 app 签名。v2.3.0 在
`src-tauri/src/infrastructure/paths.rs` 里识别 `.app` 形态并上溯三层，与 Windows 上
「exe 旁边」的语义保持一致。**升级 app 时只替换 `.app`，不要动同级的 `data/`。**

目录内容：

```
data/
├── woolbrush.db          # 交易记录 + 用户设置（含私钥，切勿外传/提交）
├── toolbar.json          # 工具栏参数
├── review/               # 复盘日志 YYYY-MM-DD_<账户尾6位>.jsonl
└── depth/                # 盘口深度采集数据（见第 5 节）
```

### 当前参数（`data/toolbar.json`）

| 字段 | 值 | 含义 |
|---|---|---|
| `askMin` | 0.920 | 买入价下限 |
| `askMax` | 0.990 | 买入价上限 |
| `orderMode` / `orderPercent` | percent / 10 | 按余额 10% 下单 |
| `slAmount` | 0.999 | 止损线 |
| `tpAmount` | 0.500 | 止盈线 |
| `scanInterval` | 0.5 | 扫描间隔（小时） |
| `timeHour` | 11 | 起始时段 |

区间取 0.92–0.99 的依据：回测显示 `askMax=0.98` 过严、显著砍掉了盈利单量，
而 `0.995` 会引入亏损单。

> 首次在 m2 上运行前，把 m5 项目里的 `data/toolbar.json` 复制到 `~/Applications/data/`，
> 否则会使用代码内置默认值。

### 必填设置

私钥、`funder_address`、`proxy_url`（第 2 节）、LLM 配置（第 3 节）。
多账户并行时，复盘日志会按账户分文件，且每行注入 `acct` 字段，合并后仍可还原来源。

## 5. 盘口深度采集

### 为什么必须尽早开始

历史盘口是**唯一无法事后补抓**的数据。Polymarket 的 `prices-history` 只有成交价序列，
没有挂单量，所以此前所有回测里的「机会数」都只是上限——无法验证深度是否足够成交。
攒够快照后，`simulate.py` 才能加上真实深度约束重跑。

### 启动

```bash
cd ~/Documents/soft/woolbrush-v2
export https_proxy=http://127.0.0.1:29758   # 代理可用后
nohup python3 backtest/collect_depth.py --interval 300 \
    >> backtest/depth_collector.log 2>&1 &
```

m2 的 `pmset sleep=0` 永不睡眠，不需要 `caffeinate`（在会睡眠的机器上才需要）。
先用 `--once --cities nyc,london` 单跑一轮验证，再挂长期任务。

### 采集范围

51 城市 × {最高温, 最低温} × 全部 11 个档位，每档位记 NO 与 YES 两侧订单簿各最多
60 档。**刻意不做价格区间过滤**——0.92–0.99 只是当前策略的区间，全量数据才能事后
回答「换到别的价格区间是否收益更高」。

实测：单轮 5 城市写入 110 条（5 × 2 × 11），NO 最优卖价从 0.00 到 1.00 各区间都有
样本，最深的盘口 52 档完整保留。全 51 城市估算每天约 130MB 原始、压缩后约 17MB。

### 输出

`data/depth/depth-YYYY-MM-DD.jsonl`，跨 UTC 日自动 gzip 旧文件。每行字段：

| 字段 | 说明 |
|---|---|
| `ts` | 采样时刻 Unix 秒（UTC） |
| `kind` | `highest` / `lowest` |
| `city` / `mdate` | 城市 slug / 该市场对应的城市本地日期 |
| `lh` | 采样时该城市的本地小时（含小数，便于按时段切片） |
| `label` | 档位标签，如 `78-79°F` |
| `tick` / `minsz` | 最小价格变动 / 交易所最小下单量 |
| `no_a` / `no_b` | NO 侧 asks / bids，`[[价, 量], ...]`，asks 升序、bids 降序，最优价在首位 |
| `yes_a` / `yes_b` | YES 侧同上 |
| `no_lt` / `yes_lt` | 最近成交价 |

两侧订单簿全空的记录（市场未开盘或已结算）不落盘。

> 这是**账户无关的公开行情**，只需在一台机器上跑一个实例。不要在多个账户的机器上
> 各跑一份，那只会得到多份完全相同的数据。m2 常开不睡眠，是最合适的宿主。

## 6. 数据回收与分析

### 复盘日志分析

```bash
python3 backtest/collect_logs.py --logs <日志目录> --out backtest/out
```

`collect_logs.py` 会扫描所有 `*.jsonl`、按内容 SHA1 去重（早期版本用
`(账户,时间戳,城市,事件,轮次)` 做键，会误删时间戳相同的不同事件，已修正），
然后输出三类结果：按价格档分布的深度统计、按账户与来源归因的闸门通过/拒绝/成交
汇总、以及可直接导入的 CSV。

### 深度数据进回测

`data/depth/*.jsonl(.gz)` 攒够后，用作 `simulate.py` 的深度约束输入，把「机会数上限」
收敛成「实际可成交数」。注意采样是 **5 分钟一个点的稀疏序列**，不是连续盘口流。

## 7. 已知未决问题

1. **m2 出网未解决**（第 2 节）。采集和交易都卡在这里，本地模型不受影响。
2. **带深度约束的回测尚未跑过**。需要先攒够第 5 节的数据。历史盘口无法补抓，
   这是目前最紧要的数据缺口。
3. **深度采样是稀疏的**。5 分钟一个点，问「13:20 进场深度够不够」只能插值。
   补偿手段：`open_execute` 日志同时记了意图价 `ask_price` 与实际成交价 `entry_price`、
   意图金额 `amount` 与实际花费 `cost`，可以反推快照到成交之间的偏差并折算成系数。
4. **YES 侧历史为空**（指 app 内 `city_snapshot` 的深度记录只存 NO 侧）。
   新的独立采集器两侧都记，所以这个缺口从启动采集之日起会被填上。
5. **夏令时切换时的市场时间窗未校验**，怀疑存在偏移，尚未确认。
6. **Polymarket 与 IEM 的结算数据源是否完全一致未校验**，存在口径差异的可能。
7. **模型选型未定**。见第 3 节的延迟权衡。
